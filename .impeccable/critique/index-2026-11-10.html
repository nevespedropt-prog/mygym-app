Design Specificity Verdict
Implementation drifts from system in critical ways

The design system in DESIGN.md is well-specified. Its most load-bearing constraint — the One Signal Rule — is violated in at least five places in the live implementation. The nav structure directly contradicts the spec's four-tab requirement. These are not minor inconsistencies; they erode the system's primary mechanisms for signalling action and structuring orientation.

Positively: Barlow Condensed uppercase is applied consistently to all headings and CTA labels. The 20px card radius and pill-shaped interactive elements are uniform. The hero gradient is used only in the hero. The token system is structurally sound — drift is at the usage level, not the definition level.

What's Working
  • Barlow Condensed uppercase applied consistently across all headings, section titles, and CTA labels — the Uppercase Display Rule holds throughout
  • Primary CTA (.cta) correctly uses red fill with white Barlow text; full-width treatment is consistent
  • 20px card radius and 999px pill radius distinction is maintained for all cards vs interactive buttons
  • Hero gradient (linear-gradient(160deg, #e03939, #a03535)) used only on the hero card — no violations of the Don't rule
  • All form inputs meet the 16px minimum font-size; iOS auto-zoom prevention holds
  • Password toggle has correct aria-label and aria-pressed; password-manager-compatible form attributes (autocomplete, name)
  • Input focus ring uses 2px solid var(--acc) exactly per spec; border becomes transparent on focus
  • Real pricing and real member quotes used throughout — no fabricated content
  • Self-hosted fonts; no external font CDN dependency; CSP clean
  • Supabase auth form uses real <form> elements with Enter/submit compatibility
  • Slot row time label uses Barlow Condensed at correct weight; status/action block correctly positioned
  • Footer carries real address, email, and legal links
Priority Issues
PI-1 P1 — Critical One Signal Rule broken in 5+ places
#e03939 (via var(--acc)) is used on elements that are not action signals or status indicators: .err error message text, .stat b stat numbers on the home view, .pbar i progress bar fill, .price-row .p price labels, and exercise error states (.exerr, .exmsg.bad). The rule's authority comes from rarity. Five non-action uses make the red signal ambiguous and weaken every actual CTA on screen.
Fix Replace color:var(--acc) on .err with a dedicated error token (e.g. --err: #c0392b or simply var(--txt) in bold). Set .stat b, .pbar i, and .price-row .p to var(--txt). Keep red only on .cta, .hbtn, .btn-small, chip backgrounds, active nav, and hero.
PI-2 P1 — Critical 6 nav tabs — no Profile, two extras not in spec
The implemented nav has: Home, Timetable, Bookings, Log, Progress, Library. The spec calls for 4 tabs: Home, Bookings, Log/Progress, Profile. There is no Profile tab in the nav; the Profile section is accessible only via a header button. Library is not in the spec at all. Six tabs at phone width make each label and icon smaller and harder to tap for the over-50s audience.
Fix options Merge Log and Progress into one tab (Log/Progress). Move Library into the Log/Progress view as a secondary segment or tab. Add a Profile tab to the nav (removes the need for a separate header button). This brings the nav to 4 tabs matching the spec and restores minimum tap-target size.
PI-3 P1 — Critical Both header buttons are ghost — log-in CTA should be red
The header has two buttons in guest mode: a ghost "Log in" (#authBtn) and a ghost "Join" (or similar secondary). The spec defines .button-header as red fill for the primary action and .button-ghost for the secondary. When both are ghost, there is no visual hierarchy and no clear primary action for first-time visitors.
Fix Remove the ghost class from #authBtn. The log-in button takes the red fill variant. The secondary action (enquiry, join) stays ghost. This matches the spec and restores the entry-point hierarchy.
PI-4 P2 — High "Do it later" on health form is a false exit
Members who skip the health and safety form via "Do it later" are silently gated — they cannot book a class until the form is completed. The button implies the form is optional; the blocked booking journey reveals it is not. This is a dark pattern and directly conflicts with Product Principle 1 (personal, not anonymous — no dark patterns).
Fix Either: (a) rename the button to "Remind me later" and show an inline banner on the booking flow explaining the requirement before the member reaches the gate, or (b) block access to the timetable immediately after sign-up with a clear one-screen explanation, so the gate is upfront rather than hidden. Option (b) aligns with the Product spec's "complete health form before booking" intent.
PI-5 P2 — High Inline style="font-size:17px" on h2 creates undocumented type size
At least one <h2> carries an inline style override setting font-size to 17px, outside the token system. The spec defines five type roles; 17px is not one of them. It sits between Body (16px) and CTA (20px) and is unreadable as a Barlow Condensed heading at that size.
Fix Remove the inline style. If the h2 genuinely needs a smaller variant, add a .h2-sm modifier to the token system at the correct size (closest spec value is CTA at 20px, or Body at 16px bold). Inline style overrides defeat the token system and are invisible to the design spec.
PI-6 P2 — Medium Member review quotes lack individual attribution
The three real member testimonials on the home view use the quote pattern correctly (red left border, no container) but do not name the member. The PRODUCT.md explicitly notes these are real, owner-verified quotes. Without a name, they read as generic filler even though they are genuine. This undermines Product Principle 1 (personal, not anonymous) and Product Principle 5 (true content only).
Fix Add a first name or first name + initial after each quote (e.g. "— Sarah M.") with owner approval. This is a content task, not a code task. Mark it as an owner to-do if names are not yet confirmed.
PI-7 P3 — Low No :focus-visible rule on .hbtn
The header button (.hbtn) does not have a :focus-visible style. The password eye toggle (.pw .eye:focus-visible) does. Keyboard-navigating users who reach the header buttons get no visible focus indicator, which fails WCAG 2.4.7 (Focus Visible) at AA level.
Fix Add .hbtn:focus-visible { outline: 2px solid var(--acc); outline-offset: 3px; } to match the existing pattern on .pw .eye.
Persona Red Flags

Over-50s and fitness beginners are a named, intended audience. Issues that disproportionately affect this group.

🧭
6-tab nav increases cognitive load for less-frequent app users Members in their 50s and 60s who open the app once a week face a wider, denser nav than the spec intended. Merging Log+Progress and adding Profile as a tab (PI-2) brings this to a manageable four.
🚧
Hidden booking gate will cause confusion and loss of trust A member who defers the health form, then tries to book a class and gets blocked, is left without a clear explanation. For a user less familiar with app conventions, this reads as a system error. The fix in PI-4 must make the gate visible at sign-up, not at booking time.
🔴
Red used on error messages is ambiguous for colour-sensitive users Using var(--acc) on error text makes errors visually identical to action signals. For users who rely on colour to distinguish errors from actions (or who have red-green colour deficiency), the distinction is lost. A dedicated error token with a distinct hue or weight difference (PI-1) addresses this.
👁
Keyboard focus gap on header buttons (PI-7) Members who use a keyboard or switch access — more common in the over-50s demographic — will find the header buttons invisible when focused. This is a WCAG AA failure that must be fixed before claiming accessibility compliance.
Minor Observations
  • .spots.full uses var(--acc) for the "FULL" state — this is a status signal and arguably within the One Signal Rule, but the red competes with the red "FULL" chip. Consider using the muted token (var(--mut)) for the spots count text when status is communicated by the chip above it.
  • The switch component (.switch) for push reminders and measurement tracking uses accent-color-style styling but is a custom element; the focus ring on the switch thumb is not explicitly defined.
  • .btn-small.ghost variant appears on the profile screen (logout, contact links) but is not in DESIGN.md's component inventory. If it's a confirmed component, add it to the sidecar.
  • The segmented control (.seg) is a recurring pattern (auth, meal plan, booking) with no DESIGN.md entry. It should be documented as a component.
  • Footer separator character (the interpunct between address fragments) may render inconsistently across OS/font combinations; use a CSS pseudo-element or explicit &middot; rather than a Unicode literal.
  • The .gymlock (access-locked) component is documented in DESIGN.md but not confirmed in the live file; if it is unused, note it as speculative in DESIGN.md.
Questions to Consider
Q1 Is Library a core daily-use feature, or is it supplementary content (exercise guides, tutorials) that members look up occasionally? If the latter, it could move into the Log/Progress view as a contextual drawer or sub-tab rather than occupying a permanent nav slot.
Q2 The health form is currently a post-sign-up deferred gate. Should it instead be a mandatory step in the sign-up flow — framed as "one quick thing before you book" — so the gate is never encountered mid-journey? The Product spec implies this intent; the implementation defers it.
Q3 The stat tiles on the home view (personal bests, session counts) use var(--acc) for the numeric values. Is this intentional — using red to signal "look at this achievement" — or is it colour bleed from the signal rule? If the former, add a named exception to DESIGN.md. If the latter, switch to var(--txt).
Q4 The profile section is currently accessed via a header button, not the nav. Assuming the nav moves to four tabs (PI-2 fix), does Profile become the fourth tab, or does the header button remain? The spec lists Profile as a nav tab; a header-button Profile creates a navigation pattern members won't expect.
Q5 The three member testimonials are labelled as real in PRODUCT.md. What is the owner's preference for attribution — first name only, first name and initial, or no attribution? This is a content decision that unblocks PI-6 and should be confirmed before the next release.
